# webloom harness — deep inventory and second harvest

Read-only inventory of `/Users/mac/workspace/webloom`, compared against the
harnex plugin's current pattern library at
`/Users/mac/workspace/harnex/plugins/harnex/templates/`.

Nothing in webloom was modified.

---

## 0. Headline

webloom is not a scaled-up version of harnex's pattern library — it is a
**second-generation harness that moved the load-bearing knowledge out of skills
and into rules, and out of rules into executable code**. Three findings dominate:

1. **The review skill is a shell.** `/webloom-review` is 33 lines. The entire
   convergent loop — caps, verify-or-revert, divergence/stuck tests, telemetry —
   lives in `.claude/rules/lenses-policy.md § Convergent loop semantics`, and the
   loop is **bracketed by two forked read-only bookends**
   (`/webloom-design-review` before code, `/webloom-critique` after) that fire on
   the *same deterministic blast-radius trigger*. harnex's `review-lenses` has one
   skill and one terminal pass.
2. **There is no `harness.toml` and no `harnex` binary.** webloom's oracle role is
   played by `nodex.toml` (a *document-graph* oracle, different subject) plus
   **67 hand-built TypeScript tool packages** under `tools/` (~60k LOC). Roughly
   30 of those are vocabulary-free and have no harnex pattern counterpart at all —
   the largest untapped seam in this harvest.
3. **A single design signature runs through everything and is portable verbatim**:
   *fail-open on inability-to-check, fail-closed on break-glass; never fabricate a
   zero; state the residual instead of implying coverage.*

Housekeeping: `.claude/worktrees/spec+aix-ops/` is a live git worktree — a full
duplicate checkout created by Claude Code's `EnterWorktree`. It is excluded from
every count below; nothing in it is a distinct harness asset.

# 2. The review chain, in depth

The operator's main review skill is `/webloom-review`, but it is only one third
of the system. **Four artifacts and one agent** make up the chain.

## 2.1 Exact invocations

```
/webloom-review [<path|dir|git-diff-range>]      # default: git diff --cached. MUTATES FILES.
/webloom-critique <path-to-file-or-dir>          # forked, read-only, model-pinned
/webloom-design-review <slug>                    # forked, read-only, self-gating on a trigger
```

`/webloom-review` also auto-invokes on fix imperatives (`"fix the findings"`,
`"apply review fixes"`, `"리뷰 반영해줘"`). Its grants are deliberately narrow and
include the *per-file* revert only:

```yaml
allowed-tools: Read Write Edit Glob Grep Bash(pnpm gate:fast) Bash(git diff *)
  Bash(git status *) Bash(git add *) Bash(git checkout -- *) Bash(scripts/hatel-emit.sh *)
```

The routing between the three is stated in the frontmatter of each:

> `description`: "…This skill modifies files. Inspection-only invariant audits
> live in `/webloom-critique`."
> `when_to_use`: "Auto-invoke on fix imperatives … Findings-only audits route to
> `/webloom-critique` (read-only)."

## 2.2 The full procedure

**The skill body is 33 lines and delegates everything.** This is the single most
important structural difference from harnex:

> Execute the convergent lens-walk loop per
> `.claude/rules/lenses-policy.md § Convergent loop semantics`. Iteration bounds,
> abort conditions, severity routing, gate:fast verification, and monotonic scope
> policy are defined there.

The eight-step loop, from `lenses-policy.md § Convergent loop semantics`:

1. **Walk** every `<id>.md` under `.claude/lenses/`, filtered by `applies_to`
   against the change-set kind.
   > "For each lens, produce a section. Silence is `<lens> no findings` — never
   > omit a lens. **Scope is monotonic** — the original change set is the scope
   > boundary; files touched only by auto-fixes do not expand the scan surface for
   > subsequent iterations."
2. **Partition** per `spec-format.md § Severity definitions`. Auto-fix candidates
   are `Critical` + `Blocker` with a non-`judgment` `rule-slug`. Everything else is
   surface-only.
3. **Apply** the concrete edit per the finding's `description`.
4. **Verify** — an atomic per-iteration revert, which is its own named abort class:
   > "run `pnpm gate:fast` after applying all fixes in the iteration. If the gate
   > passes, proceed to re-walk. If the gate fails, discard the entire iteration's
   > fixes (`git checkout -- <file>` for each touched file — the per-file form; the
   > tree-wide spellings are on `permissions.deny`, so the revert is always named
   > file by file) and abort with `aborted — gate-regression`. This prevents
   > auto-fixes from introducing type errors or lint regressions that the lens
   > re-walk cannot detect."
5. **Re-walk**, comparing against a **disk-anchored** prior set:
   > "Compare iter N+1 finding set against iter N's — against the RECORDED prior
   > set, not memory: each iteration's candidate set (its `(file:line, rule-slug)`
   > pairs) rides that iteration's own commit body — the per-iter commit template in
   > `.claude/skills/webloom-spec/phases/03-build.md § Step E` (procedure step 2) is
   > the writer — so the stuck and divergence tests below survive a compaction or a
   > resumed session and re-litigate nothing. A standalone run has no per-iter
   > commits; there the set rides the terminal report, and cross-invocation memory
   > belongs to the caller."

   And the reason only *candidates* are counted:
   > "a finding the loop is forbidden to fix is not evidence about the loop's
   > progress, and counting one makes the success condition unreachable by
   > construction while satisfying the divergence test on the first re-walk"

   Four terminal classes:
   - **Convergence** — no candidates remain → success. Surface `Major`/`Minor`/
     `[judgment]`; a surviving `[judgment]` `Critical`/`Blocker` goes there too,
     "flagged for operator decision — it is the one class the loop resolves by
     escalation rather than by edit."
   - **Monotonic divergence** — iter N+1's candidate count ≥ iter N's → `aborted — divergence`.
   - **Stuck** — same `(file:line, rule-slug)` for 3 consecutive iters → `aborted — stuck`.
   - **Iter cap** — iter > 5, "an operator-overridable default, per run and in
     conversation — `governance.md § Operator-overridable defaults vs the hard floor`".
6. **Repeat** 2–5.
7. **Report** and return control.
8. **Record self-correction depth** — a telemetry emit that cannot change the outcome:
   > "(best-effort telemetry, never blocks the loop) — emit the loop's depth so the
   > per-spec rollup surfaces review churn: `scripts/hatel-emit.sh webloom.gates
   > gate_name=polish outcome=<convergence|divergence|stuck|iter-cap|gate-regression>
   > iterations:=<final iteration count> findings:=<surviving auto-fix candidate
   > count — 0 on convergence> spec_slug=<the spec under review, or (unattributed)
   > for a standalone run>`. The seam (`scripts/hatel-emit.sh`) registers the webloom
   > Kind schema and is a silent no-op when hatel is absent (install-to-enable), so
   > the emit can never change the loop's outcome."

Per-iter commits are caller-defined. The spec polish gate commits
`spec(<slug>): polish iter <N> — <severity-tier> [<rule-slug>]` with a body line
`candidates: <file:line [rule-slug], one per finding this iter walked>`, and
`03-build.md` states why:

> "The body line is the loop's recorded state, not decoration: the next
> iteration's stuck/divergence tests compare against it … so a resumed session
> reads the prior set off `git log` instead of memory."

## 2.3 The bookends — the biggest evolution

The loop is deliberately in-session, and independence is restored **outside** it:

> "The convergent loop **edits files**, so it runs in the session context — the
> model-pinned `webloom-reviewer` agent … is read-only by design and cannot host
> an auto-fixer. In-session self-fixing is structurally weak: the fixer anchors on
> the reasoning that produced the code and reads only the surface it just edited,
> so a wrong-but-converged result reads as done. Independence is therefore restored
> at the **bookends**, not inside the loop — `/webloom-design-review` refutes the
> *design* in a forked context before code exists (front), and the spec pipeline
> runs a forked `/webloom-critique` confirmation after convergence (back)."

### Front bookend — `phases/03-build.md § Step 0` → `/webloom-design-review`

Fires on a **deterministic disjunction of named signals**, never a tuned score:

> "The trigger is a deterministic disjunction of NAMED signals (never a tuned
> score), computed from the plan's declared surface: `multi-package` (≥2 packages),
> `integration-boundary` (auth/db/observability/ai/assistant/agentic, or a
> deploy/catalog contract), `schema-migration` (closed-enum SSOT or db schema),
> `harness-change` (`.claude/rules/**`, `.claude/skills/**`, `tools/**`,
> `hooks/**`, `scripts/**`, or a root platform-contract file like `package.json` /
> `pnpm-workspace.yaml`), `constitution-tension` (a ⚠️/✗ Constitution Check row).
> A missing/unreadable plan fails closed (`plan-unreadable`)."

Its input is a structured frontmatter manifest in `plan.md`:

> "`tools/design-review-check` reads `touched:` to compute the blast-radius
> trigger … a structured array so the trigger is phrasing-independent (no prose
> parsing). … a missing, malformed, or empty manifest also fail-closes the
> design-review trigger (forces the review)."

Its re-run loop carries a **subset stall guard**, not a round count:

> "The re-run is a loop and carries the same stall guard the polish loop does, for
> the same reason: rounds that keep surfacing *new* classes are the bookend earning
> its cost, and rounds that resurface only what `## Outstanding Issues` already
> records are churn. A round whose Critical / Blocker set is a subset of the
> recorded set is a **stall** — stop looping, surface the state to the operator …
> The guard is a set comparison against what the plan already carries, not a round
> count: a count would have to be tuned, and the round that finds the deepest
> defect is often a late one."

It emits its own depth telemetry symmetrically:
`scripts/hatel-emit.sh webloom.gates gate_name=design-review outcome=<proceed|stall> …`

Its refutation discipline (Step 3):

> "1. **Ground-truth, never re-reason in the abstract.** Read the cited artefact
> (the file:line the plan points at), or run a cheap synthetic check … A refutation
> must rest on something read, not on re-derivation of the plan's own logic.
> 2. **Default-refute.** If you cannot ground-truth a decision as sound, it is
> refuted. Uncertainty resolves to a finding, not a pass."

And its `[judgment]` safety valve:

> "A refutation you cannot ground in a rule-slug, Article, or ADR carries
> **`[judgment]`** — it is surfaced for human adjudication and is NEVER auto-fixed
> (subjective design disagreement is operator territory, not a mechanical edit).
> This is the valve that stops an over-eager reviewer from coercing the plan toward
> an aspirational target."

### Back bookend — `phases/03-build.md § Step E2` → `/webloom-critique`

Reuses the *same trigger*, and the cost argument is explicit:

> "Symmetric in its gate as well as its shape: this pass fires on the same
> deterministic trigger the front bookend uses (`node tools/design-review-check/cli.ts
> <slug>`), so a change whose blast radius did not warrant refuting the design does
> not warrant a forked pass over its diff either. On `not required` the in-session
> convergence stands and Step F follows. **An always-on forked pass over every spec
> is the separate-verification-step scaffolding a self-correcting model does not
> need; the trigger is what keeps this bookend paying for itself.**"

> "Advisory in cost (no auto-fix, one forked walk), load-bearing in independence:
> it makes the BUILD bookend as fresh-context-independent as the PLAN bookend."

### Empty-report handling — stated at three separate sites

> "**Returned nothing** — an empty report is not a clean one: a critique that
> produced no findings section did not run the walk, so re-dispatch it rather than
> reading its silence as the first bullet."

And in the review skill itself:

> "read what comes back before treating it as confirmation, since a critique that
> returned no findings section did not run the walk and satisfies '0
> Critical/Blocker' the same way a clean one does — re-dispatch it rather than
> reading its silence."

## 2.4 The two doctrinal passages

> "**Independence outranks depth, and heterogeneity outranks either.** Measured
> repeatedly across specs: two reviewers run in parallel surface near-disjoint
> defect sets — an engine-independent refuter produces numeric counterexamples and
> data-model contradictions, a fresh-context lens walk produces
> completeness-versus-requirements and a11y gaps, and each rationalises what the
> other catches. The model pin on `webloom-reviewer` protects depth, but when the
> pinned reviewer is unavailable a fresh general-purpose fork still worked, because
> the property doing the work is the fresh context, not the model tier. Run the two
> lanes in parallel on a change whose failure would be expensive, and refute the
> *proposed fixes* too — no remedy inherits the reviewer's independence, and that
> holds for the **author's** fix as much as the reviewer's own: the author has just
> spent their context on the reasoning that produced it, so re-running the fresh
> pass after each fix round is part of the loop, not an epilogue
> (`docs/learnings/adversarial-2pass-convergence.md § 7. The fixer's context cannot
> audit the fixer` — two of three Major findings in one loop were introduced by the
> fix for a previous finding)."

> "**An author's completeness claim is itself a finding to check.** 'The correction
> has landed', 'the target size is met', 'the deferred requirements are recorded' —
> each is an assertion about work, not the work, and the author is structurally
> blind to the gap between the two. Reviewers have repeatedly converged on exactly
> this: a spec claiming a doc correction that was never applied, a measurable a11y
> claim asserted rather than delivered, a plan still listing requirements the build
> deferred. Read the claim against the artifact it describes, and treat a plan that
> over-claims as a defect in the plan. The loop's own anti-degeneracy guards … bound
> a *runaway* loop; they are not a substitute for the fresh-context review the
> bookends own."

## 2.5 The reviewer agent — two mechanics with no harnex counterpart

Frontmatter:

```yaml
name: webloom-reviewer
description: Fresh-context adversarial reviewer for webloom — refutes a spec plan's
  design decisions, or audits a staged change, against ground truth in the
  .claude/lenses/ vocabulary. Holds no Write or Edit tool — findings are its only
  output. Model-pinned so review depth never drops to the session model.
tools: Read, Glob, Grep, Bash, SendMessage
model: claude-opus-5
```

**Refutation as default, with the reasoning stated:**

> "Your default is **refutation**: a wrong design decision discovered after it is
> built is the most expensive correction, and same-context self-critique anchors on
> the reasoning that produced the claim (a stronger model makes a wrong claim *more*
> plausible, not less). You are pinned to a strong model so review depth is
> independent of whatever `/model` the developer's session runs — the whole point of
> living in `.claude/agents/` frontmatter rather than inheriting the session."

**One round, then retired:**

> "Your report is consumed by the dispatching skill, not a human, and it is the
> whole of your lifetime: one round, one report, then the caller retires you — a
> context that has seen its own findings is not fresh, so the next round is a new
> spawn."

**Dual-channel delivery with an explicit inert arm:**

> "Deliver it through **both** channels, in this order. First `SendMessage`: to
> `team-lead` when your startup context wraps its messages with a lead, otherwise to
> `main`, which the engine routes to the conversation that spawned you. Then the same
> content as your final message, which a fork and an unnamed spawn each hand straight
> back. Whichever arm your spawn shape does not carry is inert rather than wrong — a
> duplicate costs a line, a miss costs the round, and the caller cannot tell your
> silence from a clean pass."

**Tool-grant self-audit — the agent reports its own degraded coverage:**

> "Compare the tool set you were actually dispatched with against the `tools:` line
> in `.claude/agents/webloom-reviewer.md`, which you read from disk, and name any
> declared tool that did not arrive in your coverage boundary — a grant that fell
> short is the kind of thing only you can see, and it bounds what your review could
> reach. If `SendMessage` is among the missing, your final message is the whole of
> your delivery."

**Return contract:** Verdict (PROCEED / BLOCK with count) · Findings (one per line,
grouped by severity, each Critical/Blocker carrying ground-truth evidence) ·
**Coverage boundary** ("targets you could not read, so the operator knows where the
review is blind").

**Grant rationale stated in the body:**

> "You hold no `Write` or `Edit` tool — that absence, not a convention, is what
> makes the review non-mutating. `Bash` is granted for one reason: auditing a staged
> change set needs `git diff --cached`, which no read tool produces. Use it for reads
> only … `SendMessage` is granted for delivery, never for delegation — it creates no
> agent, and assigning work to one that already runs is outside your charge."

## 2.6 The lens contract

Frontmatter is `id` + `anchors` + `applies_to`, and **every field is lint-closed**:

```yaml
---
id: <kebab-case>            # required — matches filename basename + LENS_IDS entry
anchors:                    # required — ≥1 entry; format <source>:<id>
  - constitution:vii
  - architecture:no-shims
applies_to:                 # required — subset of LENS_APPLIES_TO
  - code

```

Six accepted anchor sources with a per-source `<id>` form:

| Source | `<id>` form | Example |
|---|---|---|
| `constitution` | lower-case roman numeral | `constitution:v` |
| `architecture` | invariant slug | `architecture:no-shims` |
| `harness-policy` | invariant slug | `harness-policy:catalog-ssot` |
| `naming-taxonomy` | section anchor | `naming-taxonomy:symbols-webloom-specific` |
| `spec-format` | lint rule id | `spec-format:plan-missing-scope-map` |

Four `harness-lint` rules behind it (`lens-anchor-unknown-source`,
`lens-anchor-unknown-id`, `lens-anchor-unreadable`, `lens-applies-to-invalid`),
plus a bidirectional `naming-lint:lens-doc` registry check:

> "**Check**: `tools/naming-lint` `lens-doc` (in `pnpm gate:fast`) fails when the
> directory and the enum disagree in either direction — a lens the loop would walk
> with an unregistered id, or an id the vocabulary offers with no lens behind it."

Two sources are **deliberately unchecked**, and the file says why:

> "`spec-format` and `naming-taxonomy` ids stay **deliberately unchecked** — the
> first names a TypeScript union with no runtime value, the second an abbreviated
> section reference no slugify rule reproduces, so either check would have to invent
> a resolution rule and would generate false positives."

Lens body discipline:

> "Lens body is free-form prose: review concerns + criteria + concrete examples +
> anti-patterns. Do not restate `governance.md` / `spec-format.md` /
> `naming-taxonomy.md` content — cite via `anchors`."

Each lens also declares its **boundary against the deterministic gate beside it**.
The `security` lens is the clearest instance:

> "The high-confidence, syntactically-decidable subset of the criteria below is now
> a non-bypassable gate: `tools/sast-lint` … flags three rules … **SSRF is
> intentionally not gated**: deciding whether a fetch URL is attacker-controlled
> needs taint analysis, which a syntactic gate cannot do without false positives …
> so it stays a `[judgment]` concern owned entirely by this lens. CSRF on
> state-mutating route handlers needs no lens rule either — `architecture.md §
> mutation-route` structurally forbids mutation-verb exports."

And `design-quality` states the three-way split among its siblings:

> "Complements its siblings rather than overlapping them: `accessibility` owns the
> WCAG criteria including reduced-motion fallbacks, `best-practice` owns token
> adherence; this lens reviews whether the rendered result reads as designed."

## 2.7 The citation grammar has a computed reader

```
[<Severity>] [<rule-slug | "judgment">] <file:line>: <description>
```

> "The computed reader of recorded findings is `tools/spec-status/outstanding.ts`:
> a row in `plan.md ## Outstanding Issues` is an unfenced line that STARTS with its
> `[Severity]` token (after list/table/bold furniture — the grammar above, a bold
> bullet, or a table row all qualify; a prose mention mid-line does not), and a row
> annotated `— **해소**: <근거>` is closed in place and no longer outstanding.
> Fenced and inline-code examples are excluded. A finding recorded in any other
> shape is one the dashboard cannot see — and a row head carrying any word outside
> the four severities is refused at commit time (`gate:specs`,
> `plan-outstanding-unknown-severity`) rather than left invisible."

`outstanding.ts` (108 LOC) is CommonMark-correct: CRLF normalised first, ATX
heading matched outside fences with ≤3 indent and optional closing `#` run,
section ends at the next level-1/2 heading outside a fence, fences pair by marker
*and* length, inline code spans stripped. The row head is **parameterised** so the
counter and the lint cannot disagree on what a row is:

```ts
export function rowHead(token: string): RegExp {
	return new RegExp(String.raw`^\s*(?:(?:[-*+]|\d{1,9}[.)])\s+)?(?:\*\*)?\|?\s*\[${token}\]`);
}
const CLOSED = /—\s*\*\*해소\*\*\s*:/;
```

Its header records the original defect: no closure detection read a fully-resolved
plan as 24 outstanding.

### Direct contradictions worth a decision

**1. Scope direction is opposite — and both call it "monotonic".**

- harnex: *"Each iteration re-walks the previous scope plus every file a fix
  touched, plus those files' prose siblings. Monotonic growth is what makes
  termination mean something: a loop that dropped files could converge by
  forgetting them."*
- webloom: *"**Scope is monotonic** — the original change set is the scope
  boundary; files touched only by auto-fixes do not expand the scan surface for
  subsequent iterations."*

harnex's is monotonic-**growing**; webloom's is monotonic-**constant**. webloom
compensates for the missing prose-sibling pass at wrapup instead (§3.1, the "made
untrue" sweep). This is a real parameterization point, not an oversight on either
side — a growing scope is safer for correctness, a constant scope is what makes
the divergence test meaningful (a growing scope can raise the count without any
regression).

**2. Down-calibration runs opposite too.**

- harnex: *"An attempt that settles nothing DOWN-CALIBRATES it — keep it, note what
  blocked the check, cap it at Major. Critical and Blocker are the tier that edits
  files and stops a gate; neither may rest on a claim the pass could not
  establish."*
- webloom reviewer: *"When a decision is unverifiable from what you can read, that
  uncertainty is itself a **finding** (default-refute), never a pass."*

The contexts differ — webloom's default-refute targets *plan design decisions*
before code exists (where a false negative is the expensive direction), harnex's
down-calibration targets *code findings* that would trigger an auto-fix (where a
false positive is the expensive direction). A pattern that ships both needs to say
which regime applies where, because the two read as contradictory when placed side
by side.

### Dropped in webloom

- **No `extensibility` lens file.** Its content is folded into
  `/webloom-design-review` Step 3: *"does it re-implement a framework primitive, or
  add an abstraction a second adopter has not asked for — the 'three rounds of
  escalating abstraction' smell?"*
- **No `root-cause` lens file.** Carried by Constitution VII + the `logic` lens's
  *"Root cause verified by reproduction"* bullet + `/webloom-debug`.
- **No prose-sibling pull into scope** (see contradiction 1).
- **No `--max-iter` flag.**
- **No "a fix is pinned or it is surfaced" rule.** harnex's `convergence.md` has it,
  backed by a measured incident: *"Measured without this, one mirror file took six
  consecutive fix-commits, one arm per round, because nothing pinned 'the two sides
  agree over all inputs' and every fresh pass found the next case."* webloom has no
  equivalent — **this is a harnex innovation the harvest should not drop.**
- **No terminal-disposition vocabulary.** harnex distinguishes `[fixed: what pinned
  it]` / `[refuted: the ground truth]` / `[accepted: who accepted it and why]`;
  webloom has one closure form, `— **해소**: <근거>`, and cannot tell a fix from an
  acceptance.
- **No "never re-attempt a recorded failed fix"** rule.
- **No "scaling the terminal pass" guidance** (partition by area / vary the lens).

### New in webloom, no harnex counterpart

- **`tools/design-review-check`** — the blast-radius trigger as an executable tool
  reading a structured `touched:` frontmatter manifest, fail-closed on absence.
- **Trigger symmetry** between the two bookends, with the cost argument stated.
- **Telemetry of review churn** on both bookends.
- **The subset stall guard** on the design-review re-run loop.
- **Reviewer dual-channel delivery** and **tool-grant self-audit**.
- **Lens-as-question reuse**: `/webloom-design-review` sharpens refutations *with*
  the lenses without walking them, so both ends of the work partition findings
  identically without the plan phase paying for a full lens walk.
- **Per-lens gate boundary declarations** (what the sibling lint owns, what stays
  `[judgment]`, and why).
- **`/webloom-critique`'s pre-flight annotation churn probe**
  (`nodex diff … | jq '.data.added_annotations[] | select(.name == "clarification_ref")'`)
  and its **on-demand domain-rule routing table** (target path → which rule file to load).

### Shell machinery

- **`hooks/_runner.sh`** (72 lines) — the most portable artefact in the repo. Two
  deliberately different anchors: `${CLAUDE_PROJECT_DIR}` (supplied on the command
  line) locates the wrapper while the agent's cwd drifts; `git rev-parse
  --show-toplevel` (inside) locates the tree, resolving to the *worktree* root which
  `CLAUDE_PROJECT_DIR` would miss. Three named skip reasons on a JSON
  `systemMessage` at exit 0 (`no-git-worktree`, `cd-failed`, `node-unavailable`,
  `unknown-verifier`), and `exec` so the verifier's exit code *becomes* the hook's.
  Presence-probes node but never its version (the floor is `.nvmrc` + `engines`).
- **`hooks/pre-commit`** — gitleaks **before** the escape hatch, with an exit-code
  trichotomy (1 = found, ≥2 = tool error, both fatal). `WEBLOOM_SKIP_GATE=1` skips
  only what follows. Telemetry timing is best-effort and preserves the RC.
- **`hooks/pre-push`** — `gate:secrets` (full-tree, un-bypassable) → escape hatch →
  artifacts/design/feedback/a11y → `gate:advisories --unattended` →
  `timeout 600`-wrapped type-check/test/build. Header states: green pre-push is
  "necessary for a green CI, not sufficient".
- **`hooks/commit-msg`** — validate-if-present `Nodex-Event:` trailer against a
  **codegenned bash array** in a sentinel region; targets bash 3.2 explicitly; uses
  `git interpret-trailers --parse`.
- **`hooks/post-format.sh`** — envelope parse + extension filter + realpath
  traversal defence + always-exit-0.
- **`scripts/hatel-emit.sh`** — 4 effective lines of install-to-enable seam.
- **`scripts/_symora.sh`** — explicitly *never a gate*; degrades to exit 127 with a
  printed textual fallback recipe.
- **`scripts/validate.sh`** — PASS/FAIL/UNMEASURED trichotomy; `wp_capture` refuses
  to launder a crash into empty JSON; per-run private browser context closed by trap;
  every echo passes through a redactor because the report is committed.
- **`scripts/_lib.sh`** — a portable half (dotted-key JSON reads via inline `node -e`,

# 6. webloom vs aix-platform divergence hints

webloom's own prose records the divergences explicitly, which is unusually convenient.

**1. Stop auditor — the sharpest divergence.** `tools/session-check/stop.ts` header:

> "Design choice (vs. aix-platform's fresh-context subprocess auditor): webloom
> catches the substantive failure modes (broken refs, frontmatter drift, contract
> violations) through `hooks/pre-commit` and `hooks/pre-push`, which own what each
> runs. The narrow gap this reminder closes is the *uncommitted* surface —
> work-in-progress the agent might forget to commit or sign off on. A subprocess
> auditor that spawns `claude -p /webloom-critique` would incur an API call on every
> turn with marginal incremental value over the existing gate suite, so this
> implementation stays in-process: a single `git status` probe + a focused reminder
> message."

harnex's `check-on-stop.sh` + `harnex guard stop-audit` sit on the **aix side** of
this split. **The pattern needs a parameter**:
`stop_audit.mode = "deterministic-probe" | "fresh-context-critique"`, keyed on
whether the project's commit-time gate suite is already dense enough that a
per-turn critique is redundant.

**2. Git env scrubbing — independently converged, differently scoped.**
`learned-patterns.md`:

> "`tools/git-env` is webloom's seam (`gitEnv` for foreign trees, `gitEnvFor` for a
> named one); aix reached the scrub half independently (`scripts/repo_root.py`
> `git_env`)."

Two harnesses reached the same defect class and only one reached both directions
(webloom's own note records that "an unconditional scrub shipped as a fix for the
foreign-tree defect and was itself a Blocker"). That asymmetry is exactly what a
shared pattern should close.

**3. Telemetry timestamp format is deliberately matched.**
`tools/telemetry/appender.ts`: *"Second precision matches aix-platform's
harness_telemetry ts format"* — evidence the two harnesses share a telemetry
ancestor with divergent Kind registries.

**4. Naming divergence.** webloom prefixes every skill `webloom-*` and every rule
`<topic>-<kind>.md` with a closed `<kind>` enum
(`conventions`/`policy`/`patterns`/`format`/`taxonomy`/`authoring`) plus four
single-word exceptions (`constitution`, `architecture`, `learned-patterns`,
`governance`). harnex's templates ship unprefixed names (`review`, `spec`,
`harness-curate`). **Parameterize the prefix**: webloom's `naming-lint:rule-doc`
check is portable, the prefix itself is not.

**5. Structural divergence: rule vs skill as the SSOT home.** webloom moved the
review loop *out of* the skill into a rule; harnex's spec-workflow moved gate
mechanics *out of* the rule into `skill/gates.md`. Both are defensible — a rule
loads path-scoped (cheap for the whole team, always current), a skill body loads
only when invoked (cheap when unused). The deciding question is whether
non-invokers need the vocabulary; webloom's answer is yes, because the design-review
skill and the build phase both speak the citation grammar without running the loop.

**6. Language substrate.** webloom is TypeScript on Node ≥ 26 with `.ts` run
natively (no transpiler) — which is why `_runner.sh` dispatches `*.ts → node`. aix
is Python/`uv`. harnex's `templates/<lang>/` split already anticipates this, but the
*tool* layer (67 packages) is written once in TS and has no cross-language story.
**A harness-tool pattern would need a language-neutral contract** — the
`{ok, data?, error?}` envelope plus an exit-code trichotomy is exactly that contract,
and webloom already isolates it in `tools/envelope/`.

**7. Cross-repo guards have no scheduled home** — a divergence *between* the two
repos, stated in `harness-policy.md § Gate aggregation`:

> "A **cross-repo** guard is the case with no scheduled home at all. … both answer
> about the **aix sibling repository's head today**, so a failure says the upstream
> moved rather than that the commit at hand is wrong, and gating on it would land an
> upstream to-do on unrelated work. … So they are **hand-run after moving aix and
> before trusting the vendored copies**."

Any harnex pattern for multi-repo verification needs this *placement* rule, not a gate.

# 8. The three things I would port first

1. **`tools/permission-rules/` + `harness-lint/hook-matcher.ts`.** harnex ships
   permission and hook templates whose grammar is currently asserted in prose.
   webloom has both grammars as measured, tested code, and it found a real defect
   doing it (`Bash(pnpm <ns>:*)` grants nothing — ten such rules read as namespace
   globs and every namespaced script prompted anyway). This is a **correctness fix
   to shipped templates**, not just an enrichment.

2. **The advisory class + the `evidence/<id>.json` freshness inversion.**
   *"An advisory never blocks; the freshness of its basis does."* harnex has
   `harness-core::evidence` with a verifier-strategy enum but no pattern that uses it
   this way. This is the single idea in webloom's harness that most changes what a
   gate suite can afford to include — it is how an expensive or stochastic
   measurement becomes trustworthy without absorbing its flakiness into retry logic.

3. **The review bookends on a shared deterministic trigger.** harnex's terminal pass
   is always-on and inside the loop. webloom's front/back bookends are forked,
   read-only, and gated by the same computed blast-radius signal — with the cost
   argument stated explicitly: *"An always-on forked pass over every spec is the
   separate-verification-step scaffolding a self-correcting model does not need; the
   trigger is what keeps this bookend paying for itself."* That sentence is the
   pattern's economic justification, and harnex's `review-lenses` currently has none.

And one thing **not** to lose in the merge: harnex's *"a fix is pinned or it is
surfaced"* rule and its three-way terminal disposition vocabulary
(`[fixed:]` / `[refuted:]` / `[accepted:]`). webloom has neither, and both are
backed by measured incidents on the harnex side.

# Appendix B — the design signature, with its instances

One sentence unifies the whole corpus, and it is stated in four different files
with four different subjects. Every instance below is portable verbatim.

## B.1 Fail-open on inability-to-check, fail-closed on break-glass

The two directions are **deliberately opposite**, and `tools/harness-lint/floor.ts`
holds both at once:

- **Violation checks fail open** — "not proven guilty". Inability to evaluate
  allows the write with a note.
- **Break-glass fails closed** — "not proven authorised". An unreadable override
  file is an absent grant, never a present one.

Instances:

| Site | Direction | Mechanism |
|---|---|---|
| `hooks/_runner.sh` | fail-open | Three skip gates, all exit 0 on a JSON `systemMessage`: `no-git-worktree`, `cd-failed`, `node-unavailable`, `unknown-verifier` |
| `tools/architecture-lint/check-pre-write.ts` | fail-open | `skip(reason)` writes `{"systemMessage":"[edit-check skipped: …]","suppressOutput":true}` and exits 0. Nine named reasons. The catch-all cannot swallow a real finding because the blocking paths `process.exit(2)` directly rather than returning |
| `tools/harness-lint/floor.ts` override | **fail-closed** | Read live from `.claude/settings.local.json`; `canonicalRepoRoot()` follows a linked worktree to the main checkout so a worktree cannot mint its own grant. A granted edit still emits a `systemMessage` — "the one signal the freeze was bypassed" |
| `hooks/pre-commit` gitleaks | **fail-closed** | Exit-code trichotomy: 1 = found, **≥2 = tool error**, both fatal. "the secret scan could not run" is a failure, not a pass |
| `tools/design-review-check` | **fail-closed** | A missing, malformed, or empty `touched:` manifest *forces* the review (`plan-unreadable`) |
| `tools/feedback-promote` | **fail-closed** | `base-ref-unavailable` / `base-parse-failed` / `observation-drift` are three named violations — "any condition that prevents enforcement surfaces as a named violation rather than a silent skip, so the contract never quietly degrades" |
| `tools/content-lint` | **fail-closed** | `inline-script-unchecked` — "an unparsed body is unverified, and a silent pass there is indistinguishable from a clean one" |
| `tools/harness-lint` (12 ids) | **fail-closed** | Every `*-unreadable` / `*-unsettled` / `*-probe-failed` rule id is a deliberate arm: inability to check is itself a finding |
| `learned-patterns.md` | doctrine | "A lint or gate that passes when its source file is missing silently disables itself — treat a missing source exactly like an unreadable one and emit a loud violation. The same trap hides in tests: seed fixtures to the real runtime state, not the degenerate empty state, or the gate becomes a no-op that the test suite certifies green." |
| `harness-policy.md` | doctrine | "A gate that consumes a generated artifact treats an absent one as a finding naming its producer, never as nothing to check: an unreadable input is the one case where a silent pass is indistinguishable from a verified one." |

## B.2 Never fabricate a zero

A measured zero and an unmeasured absence are different facts and must render
differently.

| Site | Vocabulary |
|---|---|
| `tools/retirement-audit/metrics.ts` | `export type SignalCount = number \| "unmeasured"` — "a fabricated zero reads as a measured silence and drags the classifier toward a false candidate verdict". The skill-invocation reader deliberately reads the ledger **unbounded** so it can check the ledger *reaches back* to the window start; if `oldest > cutoff` it returns `"unmeasured"` |
| `governance.md § Retirement criteria` | "any `unmeasured` component makes silence unknowable: the audit reports the gap and withholds the candidate verdict rather than inventing the answer" |
| `scripts/validate.sh` + `specs/_template/validate.md` | `PASS` / `WARN` / `FAIL` / `UNMEASURED`, exit `0` / `1` / `2`. "`UNMEASURED` is the script's third state, for a check whose instrument could not answer, and it is neither a pass nor a failure" |
| `phases/04-verify.md` | "If nothing failed but the run is `INCOMPLETE`, an unobserved check is not a passing one … `approved` is not available, because it reads as all-PASS" |
| `architecture.md § declared-token` | "'nothing was read' must never render as 'nothing was wrong'" |
| `learned-patterns.md` | "`?? 0` / `?? []` collapses two distinct absences — 'never recorded' and 'measured as empty' — into one rendered state. Carry the absence to the surface as absence (null, or an explicit `unmeasured` / `sample_zero` / `degenerate` vocabulary). Bias every uncertainty toward absent; a verdict must never falsely assert the trustworthy positive." |
| `learned-patterns.md` | "When a check genuinely cannot run, record WARN with rationale — never lower the bar to PASS." |
| `md-wisely-doc-check` | An absent sibling repo yields a **passing envelope naming the reason** — "a tool that quietly succeeds because it could not find its input has the exact shape of the bug it exists to catch" |
| Review chain (3 sites) | "an empty report is not a clean one: a critique that produced no findings section did not run the walk, so re-dispatch it rather than reading its silence" |
| `governance.md § Agentic execution defaults` | "a completion is not a result, so an empty return is read as the degradation it is and never as a clean pass — a forked review that reported nothing is not a review that found nothing" |
| `retirement-audit` cat-file reader | "the unresolved form echoes the request spec, so a desync throws rather than silently returning a short read that would read as a measured zero" |

## B.3 State the residual instead of implying coverage

| Site | Passage |
|---|---|
| `harness-policy.md § destructive-filter` | "**This is a tripwire, not a boundary, and the residual is the grammar's own.** A starred rule cannot constrain what follows its star … `git checkout -b tmp --force` **does** discard uncommitted work and **is** granted by `Bash(git checkout -b *)` (both measured) … the honest alternatives are dropping the grant so ordinary branch work prompts, or keeping it and stating this." |
| `harness-policy.md § floor-integrity` | "local hook enforcement is inherently bypassable (a shell is Turing-complete), so the authoritative guarantee is the **server-side CI re-run**" |
| `architecture.md` | "The guarantee is asymmetric — **false-positives are structurally excluded; false-negatives are possible**. A clean prop is never misflagged, so a flag is always actionable; a green run is not proof of absence" |
| `closed-enums-taxonomy.md` | "`gate:closed-enums` … does not by itself forbid a rename … The single-commit-refactor-every-consumer discipline is therefore a review contract, not a single blocking gate." |
| `content-format.md` | Known non-coverage stated with a **measured size**: "108 of the corpus's headings are built that way, across twelve documents" |
| `security` lens | "**SSRF is intentionally not gated**: deciding whether a fetch URL is attacker-controlled needs taint analysis, which a syntactic gate cannot do without false positives … so it stays a `[judgment]` concern owned entirely by this lens" |
| `lenses-policy.md` | "`spec-format` and `naming-taxonomy` ids stay **deliberately unchecked** … either check would have to invent a resolution rule and would generate false positives" |
| `sast-lint` | Documented blind spots not chased: spread-prop and `React.createElement` XSS forms, values built in a prior variable, aliased sinks, dynamic `import()` |
| `md-wisely-doc-check` | Explicitly NOT verified: that the quoted *text* still matches — "excerpts are editorially re-wrapped/elided with no mechanical inverse, a checker claiming to verify them would be guessing" |
| Reviewer agent + critique + review skills | **Coverage boundary** is a required section: "targets you could not read, so the operator knows where the review is blind" / "so a partial audit never reads as exhaustive" |
| `learned-patterns.md` | "A sweep claim states the predicate that ran, the count it returned, and how that count was triaged — never that the sweep was exhaustive." |

## B.4 One wrapper, one object, exit code passes through

- `hooks/_runner.sh` `exec`s the verifier so its exit code *becomes* the hook's;
  `harness-lint:hook-bypass-wrapper` enforces that every settings.json command
  carries exactly that prefix.
- `tools/session-check` buffers a **single** output object so a late throw joins
  the same JSON rather than appending a second unparseable one, and owns
  always-exit-0 structurally at the entrypoint.
- `harness-policy.md`: "A verifier emits **one** object per run."
- Channel by audience: `systemMessage` for the operator,
  `hookSpecificOutput.additionalContext` for the agent; plain exit-0 stdout is
  per-event and therefore "not a wrong channel so much as an **audience-wrong** one".
- `check-pre-write.ts` splits the two channels deliberately: `systemMessage` for a
  skip, **stderr for the exit-2 paths** where the hook contract feeds it back to
  the model.

## B.5 The escape hatch never covers the secret scan

`harness-policy.md § destructive-filter` gives this its own table — one invariant,
three surfaces, one home:

> "**`WEBLOOM_SKIP_GATE=1` — one invariant, three surfaces.** The invariant is
> universal: *it never skips the secret scan*, which runs first and unconditionally
> at both git hooks. What it does skip is per surface, and this table is the one
> home — every other site cites it rather than restating a member list. … A skip is
> loud at every surface (the hook prints what it skipped) and carries its reason in
> the commit message."

`hooks/pre-commit` implements it in exactly that order: gitleaks runs, then the
escape hatch is read, and the skip message says so — "the secret scan already ran".
